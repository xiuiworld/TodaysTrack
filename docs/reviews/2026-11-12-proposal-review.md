# 두 기획서 심사 검토 및 보완내역

검토일: 2026년 11월 12일

현재 문서의 성격: 아래는 인터뷰와 AI 생성 방향 확정 전의 검토 이력입니다. 규칙 기반 작곡·동일 악보·AI 편곡 보조에 관한 제안은 현재 요구가 아닙니다. 최신 방향은 [내부 제품 기획서](../product/product-plan.md)와 [제출용 기획서](../proposal.md)를 따릅니다. 경쟁 조사는 이후 [별도 보고서](../research/competitive-analysis-2026-11-12.md)로 보완했습니다. 아래 과거 평가를 최신 문서에 대한 재심사 결과로 해석하지 않습니다.

문서 정리 메모: 검토 당시 ‘드라이브 앨범’으로 표기한 후보가 이후 ‘오늘의 트랙 (Today's Track)’으로 선정·명명되었습니다. 아래 평가는 당시 명칭을 유지합니다. 현재 기획서는 [오늘의 트랙 기획서](../proposal.md), 다른 후보는 [조수석 선물 보관본](../archive/passenger-gift-proposal.md)에서 확인할 수 있습니다.

이 문서는 공식 심사 기준에 비춰 작성한 사전 검토 의견입니다. 실제 심사위원의 평가나 합격 가능성 예측은 아닙니다. 두 기획서는 구현·고객 검증 이전의 계획으로 평가했으며, 공식 배점이 공개되지 않아 점수나 임의 가중치를 만들지 않았습니다.

## 1. 적용 기준과 검토 범위

공식 1차 서류심사는 차량 특화성, 창의성, 기술 활용성, 사업성을 필수로 평가합니다. 개발 산출물은 선택 제출 시 단계별 가산점 대상입니다. 세부 배점은 비공개이고, 공식 안내의 2차 PT 세부 기준은 추후 안내 항목입니다. 본 검토는 공개된 1차 기준을 적용했습니다.

두 문서의 1~6번을 수정하고 7번 참고자료는 공란으로 유지했습니다. 참가자 개인정보, 가상의 개발 결과, 사용자 조사 결과나 사용자 수를 추가하지 않았습니다. 주행 후·주행 중 음악 생성 모두 가능하다는 기존 방향을 유지하되, 드라이브 앨범의 기본 개발 계획은 주행 후 생성에 집중했습니다.

근거: [공식 심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards), [개발 범위 공지](https://appdevchallenge.auto-hmg.io/notice/c0a1a000-2026-4923-8000-000000000008).

## 2. 심사위원 관점의 비교

| 기준 | 드라이브 앨범 — 원문 평가 | 조수석 선물 — 원문 평가 |
| --- | --- | --- |
| 차량 특화성 | 여정을 음악으로 만든다는 연결은 있으나 위치·시간만으로 끝나면 휴대폰 기록과 차이가 작다. 차량 정보가 실제로 어떤 음악을 바꾸는지 불명확하다. | 개인 메시지를 전달하는 장면은 이해하기 쉽지만, 예약 재생·플레이리스트와의 차이가 약하다. 내비 연동을 향후 기능으로 미뤄 차량의 역할이 제한된다. |
| 창의성 | 여행을 음악으로 소장하는 경험은 흥미롭다. 그러나 AI에 분위기를 요청하는 수준이면 아이디어의 고유성이 약해진다. | 선물이라는 고객 동기는 분명하다. 다만 개인 콘텐츠, 시간, 장소가 어떻게 결합되는지가 구체적으로 보여야 한다. |
| 기술 활용성 | 음악 API와 규칙 기반 엔진 중 구현 방식이 미정이고, AI가 테마나 구간을 지키는지 불확실하다. 핵심 결과물의 개발 위험이 크다. | 카드·재생 구조는 비교적 명확하다. 장소를 벗어난 뒤 대기 메시지가 재생되는 문제, 이동 지연, 음원 이용 조건과 제작 범위가 덜 정리돼 있다. |
| 사업성 | 타깃이 넓고, 음악을 다시 듣거나 다음 여행에서 또 생성할 근거가 부족하다. 음악 생성 비용과 과금 가설이 연결되지 않는다. | 타깃을 기념일로 좁힐 여지가 있다. 다만 제작 부담과 낮은 이용 빈도를 해결하지 않으면 한 번 쓰는 이벤트에 머물 수 있다. |

기획만 비교하면 드라이브 앨범은 음악으로 설득할 수 있을 때 차별화 여지가 있고, 조수석 선물은 고객 장면과 구현 흐름을 구체화하기 쉽습니다. 어느 쪽도 현재 문서만으로 수상 경쟁력을 입증한 상태는 아닙니다.

## 3. 드라이브 앨범 보완

### 주요 예상 질문

1. 여행 정보를 AI에 입력해 만든 음악과 무엇이 다른가?
2. 같은 기록이면 같은 음악이 나오는가? 다른 기록의 차이가 실제로 들리는가?
3. 음악이 듣기 좋다는 근거가 있는가?
4. 차량 SDK가 없어도 휴대폰으로 만들 수 있는 것 아닌가?
5. 외부 음악 API를 쓰지 못하거나 생성 비용이 높으면 어떻게 구현할 것인가?

### 문서에 반영한 보완

- 초기 고객을 ‘동행자와 주말 여행을 즐기고 음악 기념물을 남기고 싶은 차량 이용자’로 좁혔습니다. 고객의 소장·재감상 의향은 검증 전 가설로 표시했습니다.
- 주행 기록에서 기본 악보와 편곡 구성을 만드는 과정을 구체화했습니다. 방향 변화 패턴은 제한된 음계의 테마로, 구간 비중은 악절 길이로, 방문 지점은 편성 변화로 연결합니다.
- 동일 기록·스타일·엔진 버전의 기본 악보를 재현 가능하게 설계했습니다. 음악과 주행의 인과관계를 설명하고 비교할 근거를 추가했습니다.
- 기본 생성은 규칙 기반 악보·편곡과 음원 렌더링으로 명확히 하고, AI는 검증 후 확장할 보조 수단으로 정리했습니다. 핵심 경험이 특정 외부 AI API에 전적으로 의존하는 위험을 줄였습니다.
- Vehicle SDK의 트립 거리·시간과 위치 기록의 역할을 구분했습니다. 차량 정보가 없으면 이를 반영한 결과라고 표시하지 않도록 했습니다. 주행 모드 등 역할이 약한 정보의 나열은 줄였습니다.
- 같은 스타일의 여정 미반영 곡과 여정 반영 곡을 비교하도록 했습니다. 감상 품질과 개인화 효과를 별도로 확인하고, 위치만 사용한 경우와 차량 정보를 사용한 경우도 구분하도록 했습니다.
- 반복 생성 없이 완성 음원을 다시 감상하는 구조와 추가 편곡·스타일 과금 가설을 연결했습니다. 음악 만족이 저장·공유·다음 여행 사용으로 이어지는지를 확인하도록 했습니다.

### 문구 수정으로 해결되지 않은 부분

- 실제 음원이 듣기 좋은지, 주행과의 연결이 지각되는지는 아직 확인되지 않았습니다.
- 규칙 기반 작곡·렌더링의 구현 품질과 Pleos 환경 자원 사용은 검증 전입니다. 구현 방향을 구체화한 것이 구현 완료를 의미하지 않습니다.
- 필요한 차량 값의 실제 수신과 기여를 확인해야 합니다. 위치만으로도 가능한 기능이라는 한계가 완전히 해소된 것은 아닙니다.
- 동일·유사 서비스를 배제하는 전체 경쟁 조사는 수행하지 않았습니다. 최초·유일한 서비스라고 주장하지 않습니다.

## 4. 조수석 선물 보완

### 주요 예상 질문

1. 휴대폰 예약 메시지·플레이리스트 대신 차량 앱을 써야 하는 이유는 무엇인가?
2. 내용을 직접 준비해야 한다면 제작을 끝낼 사람이 얼마나 되는가?
3. 목적지나 경로가 바뀌면 메시지가 엉뚱한 곳에서 재생되지 않는가?
4. 좋아하는 음악을 실제로 재생할 수 있는가? 외부 스트리밍 제어가 필요한가?
5. 생일에 한 번 쓰는 서비스가 사업이 될 수 있는가?

### 문서에 반영한 보완

- 초기 고객을 ‘연인의 생일·기념일 이동을 준비하는 운전자’로 좁혔습니다.
- 환영·추억·마지막 편지의 최소 제작 흐름을 정하고, 음악·질문은 선택 항목으로 정리했습니다. 템플릿, 미리듣기와 다음 행사의 복제·수정 흐름으로 제작 부담을 줄이는 계획을 추가했습니다.
- 내비게이션 목적지 확인을 기본 개발 범위에 포함했습니다. 콘텐츠의 목적지, 실제 장소 진입, 재생 순서, 오디오 중단·재개를 연결하는 점을 차별화 가설로 설명했습니다. 휴대폰에서 불가능한 기능이라고 과장하지 않았습니다.
- 실제 출발 자동 감지와 프로그램 시작 시점을 구분했습니다. 시간 카드는 프로그램 시작 이후의 경과 시간을 기준으로 하며, 사용자 입력 예상 시간과 실제 도착 예정 시간도 구분했습니다.
- 장소 진입 후 대기하던 카드가 재생되기 전에 유효 범위를 다시 확인하고, 벗어났으면 보류하도록 했습니다. 필수 메시지 우선순위와 재생 중인 메시지의 보호 규칙을 정리했습니다.
- 기본 시연은 이용 범위가 확인된 음원과 TTS로 구성하고, 외부 스트리밍 서비스를 임의 제어할 수 있다고 전제하지 않았습니다. 음성 합성의 네트워크 의존성도 미확인 항목으로 구분했습니다.
- 미래 카드의 본문을 숨기고, 동승자가 원하지 않을 때 중단할 수 있도록 했습니다. 휴대폰 퀴즈 응답은 첫 구현에서 제외해 범위를 정리했습니다.
- 저빈도 서비스에 구독을 전제하지 않고 프로그램 단위 구매를 가설로 정리했습니다. 제작 완료, 차량 실행, 경험 완료, 다음 행사 재사용을 나눠 측정하도록 했습니다.
- 휴대폰 수동 재생과 비교해 진행 조작, 전달 시점과 만족도가 개선되는지를 확인하는 계획을 추가했습니다.

### 문구 수정으로 해결되지 않은 부분

- 제작이 쉬운지와 상대방이 실제로 좋아하는지는 사용자 체험 전입니다.
- NaviHelper 목적지 조회와 음성 합성·오디오 포커스의 실제 작동은 에뮬레이터에서 확인해야 합니다.
- 위치 기반 콘텐츠 경험의 일부는 휴대폰에서도 구현할 수 있습니다. 차량 통합이 충분한 이점을 주는지 검증해야 합니다.
- 이벤트 빈도, 유료 구매 의향과 운영 원가는 아직 확인되지 않았습니다.

## 5. 제출 전 우선 확보할 증거

이 항목은 기획서의 설득력을 높이기 위한 권고이며, 임의로 추가한 공식 지원 요건은 아닙니다. 참고자료는 사용자 요청에 따라 두 기획서 모두 공란으로 유지했습니다.

| 기획 | 우선 확보할 증거 | 심사 기준과의 연결 |
| --- | --- | --- |
| 드라이브 앨범 | 서로 다른 기록으로 만든 실제 음원과 기록→음악 요소의 대응 화면 | 창의성·기술 활용성 |
| 드라이브 앨범 | SDK 수신 정보와 음악에 반영된 부분을 함께 보여주는 시연 | 차량 특화성·기술 활용성 |
| 드라이브 앨범 | 감상 품질과 여행 기념물로서의 소장 의향 평가 | 고객 니즈·사업성 |
| 조수석 선물 | 짧은 제작부터 차량 실행까지 이어지는 시연 | 고객 니즈·기술 활용성 |
| 조수석 선물 | 정상 경로와 장소를 건너뛴 경로에서 다르게 진행되는 시연 | 차량 특화성·기술 활용성 |
| 조수석 선물 | 제작자와 동승자의 체험, 수동 재생과의 비교 | 고객 니즈·사업성 |

문서 보완 후에도 드라이브 앨범의 가장 큰 승부처는 실제 음악이며, 조수석 선물의 가장 큰 승부처는 적은 준비로 충분히 개인적인 경험을 전달하는지입니다. 두 기획의 결합과 신규 기능 추가는 이번 수정 범위에 포함하지 않았습니다.

## 6. 확인한 기술 근거

- [FusedLocation SDK](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro): 위치 업데이트, 지정 영역 진입·이탈 알림, 지원 환경 확인.
- [Vehicle SDK](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/intro): 차량 도메인별 조회·제어와 기능 지원 확인. 실제 사용 가능 값은 런타임 검증 대상.
- [NaviHelper SDK](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/intro): 목적지 확인 등 내비 연동. 이벤트는 내비 앱 구현과 현재 상태에 따라 달라질 수 있음.

위 문서 확인은 API 존재에 관한 근거이며, 두 앱의 실제 동작 검증 결과가 아닙니다. 공모전 에뮬레이터 개발 범위와 실제 앱 마켓 배포의 별도 권한·심사 조건도 구분해야 합니다.
