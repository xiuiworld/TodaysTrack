# 오늘의 트랙 · 내부 제품 기획서

작성·개정일: 2026-11-12 · 버전: 0.2 · 단계: 제품 기획

이 문서는 **누구에게 어떤 경험을 제공하고, 어떤 범위와 원칙으로 만들 것인가**를 정하는 내부 기준이다. [제출용 기획서](../proposal.md)는 외부 심사자를 위한 설명으로 별도 관리한다. 근거는 [경쟁 조사](../research/competitive-analysis-2026-11-12.md)에 있다.

기획에 필요한 기능·이용 흐름·데이터 활용 방향은 유지한다. API 계약, 데이터 모델, 서비스 구조, 상태 전이, 동기화 방식은 후속 설계에서 정한다. 기존 기술 검토는 [설계 단계로 넘길 메모](../design/deferred-design-notes.md)로 분리했다. 이 메모는 확정 설계가 아니다.

**상태 구분:** ‘사용자 방향’은 대화에서 정한 제품 의도, ‘작업 기본값’은 위임받아 정한 변경 가능한 동작, ‘제안’은 미확정 구체화, ‘검증 과제’는 실제 자료·시제품으로 확인할 사항이다. 앱 구현·SDK 수신·생성 음원·고객 반응은 모두 검증 전이다.

## 1. CAPABILITY — 제품의 핵심 경험

### 1.1 제품 정의

> **함께 달린 여정을, 다시 들을 수 있는 한 곡으로 남긴다.**

오늘의 트랙은 차량에서 수집한 실제 주행 기록을 바탕으로, **주행이 끝난 뒤 AI가 전체 여정의 분위기와 흐름을 담은 곡을 만드는 Pleos Connect 앱**이다. 사용자는 운전 중 별도로 촬영하거나 작곡하지 않아도 이동을 음악의 재료로 남기고, 완성곡을 다시 듣거나 동행자와 나눌 수 있다.

주행 후에는 출발·중간 이동·방문·귀환까지 전체를 보고 한 곡의 도입·전개·마무리를 구성할 수 있다. 이 특성을 실제 음악 결과에 활용하는 것이 중심이다. 앨범·폰 연계·선택 설정은 이 경험을 편하게 시작하고 오래 소장하게 하는 기능이다. 설정의 수나 앨범 관리의 복잡성을 제품의 중심으로 키우지 않는다.

### 1.2 고객과 니즈

초기 검증 대상은 **음악을 즐기며 친구·연인 등과 드라이브·여행한 시간을 개인적인 콘텐츠로 남기고 싶은 Pleos Connect 이용자**다. 차량 이용자 모두를 첫 타깃으로 잡지 않는다. 동승자는 공동 감상자이자 결과물 공유의 대상이다.

고객 과업은 “같이 다녀온 시간을 그냥 흘려보내기 아쉬울 때, 많은 입력이나 편집 없이 그날을 다시 떠올릴 음악을 남기고 싶다”이다. 기능적 불편의 해소와 함께, 자기 이동이 창작물이 되는 신선함을 제공한다.

사진·영상·기존 플레이리스트로 충분하다고 느끼는 사람도 있다. 생성곡이 실제로 듣기 좋은지, 여정을 담았다는 사실이 소장 가치를 더하는지는 가설이다. 매일 음악 기록을 쌓고 싶은 이용자는 확장 사용 유형으로 다루되, 특별한 드라이브와 일상의 반복 사용을 모두 입증했다고 주장하지 않는다.

### 1.3 경쟁과 구별할 제품 가치

| 관점 | 오늘의 트랙의 방향 | 확인할 점 |
| --- | --- | --- |
| 주행 중 반응형 음악과의 구별 | 완료된 전체 여정을 바탕으로 시작과 끝이 있는 곡 생성 | 주행 후라는 특성이 곡의 전개에 드러나는가 |
| 휴대폰 센서·GPX 도구와의 구별 | 위치와 함께 지원되는 차량 거리·시간 등의 SDK 기록을 생성 재료로 사용 | 차량 정보의 기여가 있고 설명 가능한가 |
| 풍경 음악화와의 구별 | 사용자가 다녀온 여정 전체의 음악적 회고에 초점 | 카메라 접근을 전제로 하지 않고도 가치가 성립하는가 |
| 일반 AI 음악 생성과의 구별 | 여행을 긴 글로 재구성하지 않아도 실제 기록에서 곡의 구성안을 만듦 | 일반적인 분위기 요청보다 의미 있는 결과인가 |
| 결과물의 지속 가치 | 곡을 보관·재감상하고 월간·여행 앨범으로 묶어 소장 | 다시 듣고 다음 기록을 남길 이유가 있는가 |

AudioDrive는 휴대폰 센서를 사용하므로 ‘데이터 없는 음악’으로 표현하지 않는다. Geosonify의 공개자료는 좌표·GPX 기반이며 차량 SDK 연동은 확인하지 못했다. Kia Soundscapes와 Drive-to-Music은 중요한 인접 사례다. 근거와 한계는 [경쟁 조사](../research/competitive-analysis-2026-11-12.md)를 따른다.

이 차이는 제품 경험과 데이터 활용의 조합에 관한 것이다. 최초성·수상 가능성·음질 우열을 입증한 결론은 아니다. **폰에서 첫 곡 생성을 막는 정책만으로 차량의 독자적인 가치가 생기지는 않는다.** 실제 차량 기록과 차량 내 이용 흐름의 기여를 확인해야 한다.

## 2. CONSTRAINTS — 확정 방향과 제품 원칙

### 2.1 대화에서 이어받은 기준

| 항목 | 구분 | 반영 내용 |
| --- | --- | --- |
| 이름 | 사용자 방향 | 오늘의 트랙 / Today's Track. 폴더명 TodaysTrack. |
| 중심 아이디어 | 사용자 방향 | 실제 주행이 끝난 뒤 그 기록으로 AI가 곡을 만든다. |
| 생성 역할 | 사용자 방향 | AI가 실제 곡을 생성한다. 규칙 기반 음표 작곡 엔진이나 AI 편곡 보조를 기본 방식으로 확정하지 않는다. |
| 반영 수준 | 사용자 방향 | 여정의 전체 분위기와 구간·사건의 흐름을 함께 담는다. |
| 가사·장르 | 사용자 방향 | 가사 있는 노래·무가사 연주곡과 장르를 선택하되 선택은 최소화한다. |
| 사진·메모 | 사용자 방향 | 선택 입력. 없어도 곡을 만들 수 있다. |
| 기록 기간 | 사용자 방향 | 초기 설정에서 하루·여행 단위를 고르고 이후 변경 가능하게 한다. |
| 생성 기본 동작 | 작업 기본값 | 기록이 모이면 알려주고 한 번 눌러 생성. 자동 생성·원하는 기간 선택 생성은 설정으로 제공한다. |
| 앨범 | 사용자 방향 | 하루 곡들을 월간 앨범으로, 여행 기록의 곡들을 여행 앨범으로 소장할 수 있다. |
| 폰 연계 | 사용자 방향을 반영한 현재 해석 | 새 기록의 첫 곡은 차량에서 생성한다. 폰에서도 기존 곡 재생성·편집·앨범 관리·감상·보관·다운로드·공유 등을 제공한다. |
| 기획의 중심 | 사용자 보정 | 설정·앨범·폰 기능이 핵심 주행 음악 경험을 대체하거나 과도하게 부각되지 않도록 한다. |
| 문서 단계 | 사용자 방향 | 지금은 기획 단계. 상세 설계는 이후 별도 진행한다. |
| 제출 자료 | 유지 조건 | 제출용 7번 공란. 개인정보·가상 성과·미확인 구현 결과를 넣지 않는다. |

실시간 주행 음악은 이전 대화에서 허용한 확장 가능성으로 남긴다. 현재 기획의 핵심 및 필수 완료 조건은 주행 후 생성이다.

### 2.2 사용성과 신뢰

- 선택한 가사·장르·기록 기준을 기억한다. 매번 설문처럼 다시 묻지 않는다.
- 최초 추천 음악 설정은 제공하되 구체적인 기본 장르는 아직 미정이다. 추천을 실제로 학습한 개인 취향처럼 표시하지 않는다.
- 자동 생성 여부·범위를 알리고 변경·중지할 수 있게 한다. 기간 설정을 무조건 자동·유료 생성에 대한 동의로 취급하지 않는다.
- 주행하지 않은 날의 곡이나 관측하지 못한 구간을 실제 차량 기록으로 만들어 채우지 않는다.
- 기록 사실·사용자 입력·사진의 추정 정보·AI의 창작 표현을 구분한다. 관계·감정·날씨·장소를 임의의 사실로 만들지 않는다.
- 와이퍼를 쓰더라도 강우량을 측정했다고 표현하지 않는다. 이동 특성을 운전 실력·감정 진단으로 바꾸지 않는다.
- 사용 데이터와 곡 구성안을 설명하되 AI가 지켰는지 확인하지 않은 음표·초 단위 대응은 보장하지 않는다.
- 같은 입력의 반복 생성도 다른 곡이 나올 수 있다. 재감상은 저장된 음원을 사용한다.

### 2.3 차량·개인정보 경계

정차 중 준비·생성·편집하고, 주행 중에는 기록을 위해 반복 조작을 요구하지 않는다. 화면 제한과 오디오 공존은 차량 플랫폼 정책을 따른다.

정밀 경로의 기본 보관 위치는 차량 로컬로 제안한다. 음악 생성에는 필요한 요약 특징만 외부 전달하는 방향을 검토한다. 폰에 동기화할 정보·정밀 경로의 전달 여부·선택 사진과 메모의 분석 범위는 사용자가 이해할 수 있게 구분하고 후속 설계에서 정한다. 특징을 줄였다고 완전 익명화라고 단정하지 않는다.

다운로드·공유는 제품 기능에 포함하지만 실제 제공 범위는 음악 서비스의 계약과 결과물 이용 조건을 확인해야 한다. 이를 이미 확보한 권리나 배포 완료로 표현하지 않는다.

## 3. IMPLEMENTATION CONTRACT — 기획 단계의 기능과 이용 흐름

사용자에게 필요한 동작·입력·결과·실패 시 경험까지만 정의한다. 함수 서명·데이터베이스·서버 구성·상태 머신은 정하지 않는다.

### 3.1 핵심 이용 흐름

**차량에서 기록 → 주행 종료 후 전체 여정 정리 → 곡의 구성안 작성 → AI 음악 생성 → 감상·소장**

처음 설정 뒤에는 기본 흐름의 추가 선택을 최소화한다. 설정 변경·사진·메모는 원할 때 열고, 이용하지 않아도 완성곡을 받을 수 있도록 한다.

| 과정 | 이용자가 하는 일 | 앱이 제공할 결과 |
| --- | --- | --- |
| 초기 설정 | 하루·여행 기준 선택. 음악 설정은 추천 사용 또는 변경 | 기억되는 설정과 기록 목적 안내 |
| 주행 기록 | 기록을 시작하고 운전 | 지원 데이터 수집 및 수신 상태 표시 |
| 기록 마무리 | 하루·여행을 마치거나 원하는 기록 범위를 선택 | 실제 수집 기록의 요약·누락 안내 |
| 음악 만들기 | 기본 설정으로 한 번 눌러 실행. 사진·메모는 선택 | 선택 기간의 흐름·분위기를 담은 AI 생성곡 |
| 감상·저장 | 완성곡을 듣고 간직 | 곡·제목·커버·기록 요약 |
| 이후 이용 | 폰과 차량에서 재감상·편집·재생성·앨범 관리 | 이동이 끝난 뒤에도 이어지는 소장 경험 |

### 3.2 주행 기록을 곡에 반영하는 방식

앱은 실제 기록에서 **음악으로 표현할 여정의 특징과 전체 구성안**을 만든다. AI는 이를 바탕으로 멜로디·화성·보컬 또는 연주와 최종 음원을 생성한다. 기록 해석에 규칙을 사용하더라도 실제 작곡을 규칙 기반 음표 엔진으로 고정하는 것과는 다르다.

| 재료 | 곡에 요청할 표현 | 확인할 경계 |
| --- | --- | --- |
| 출발 시간대·선택 장르 | 곡 전체의 색채·분위기 | 감정 측정으로 표현하지 않음 |
| 이동 구간의 순서·상대적 비중 | 도입·중심 전개·마무리의 구성과 비중 | 실제 시간의 정밀한 축소 재생은 아님 |
| 정리한 경로 변화 | 반복·변화의 정도와 전개 대비 | GPS 흔들림을 의미 있는 이동으로 해석하지 않음 |
| 지원 차량 거리·트립 시간 | 위치와 함께 이동 규모·구간 비중을 해석해 전개 구성에 사용 | 단위·시간 의미·리셋·지원 여부를 확인 |
| 확인된 방문 | 악기·분위기가 전환되는 구간의 소재 | 장소 지정과 실제 방문을 구분 |
| 확인된 귀환 | 도입의 음악적 분위기를 회고하는 마무리 요청 | 같은 멜로디 재등장 보장은 별도 검증 |
| 선택 사진·메모 | 남기고 싶은 장면·이야기를 가사·커버에 반영 | 사진만으로 지명·관계·감정을 확정하지 않음 |
| 선택 확장: 와이퍼 | 일부 음악 질감의 소재 | 날씨의 확정 사실로 바꾸지 않음 |

이 연결은 앱의 음악적 해석이다. 데이터가 어떤 구성 요청에 쓰였는지와 실제 곡이 그 요청을 따랐는지는 따로 확인한다. 실패한 요청을 곡이 충실히 반영했다고 안내하지 않는다.

곡과 함께 출발–중간 이동–귀환 같은 여정 요약을 보여주는 방향이다. 재생 구간과 지도의 정밀한 동기화는 기본 약속에 넣지 않는다. 검증된 대응 방법이 있을 때 확장한다.

### 3.3 가사·장르·선택 입력

| 항목 | 기본 경험 | 선택 변경 |
| --- | --- | --- |
| 가사 여부 | 추천 또는 이전 선택 사용 | 가사 있는 노래 / 무가사 연주곡 |
| 장르 | 추천 또는 이전 선택 사용 | 소수 장르에서 변경. 목록은 청취 후 결정 |
| 사진·메모 | 입력 없이 진행 가능 | 원하는 장면·한 줄 이야기 추가 |
| 제목·커버 | 자동 제안으로 저장 가능 | 정차 중 또는 폰에서 수정 |

가사 있는 노래도 메모 입력을 필수로 만들지 않는다. 기록만으로 만들 때는 확인한 여정 특징과 창작 표현을 사용한다. 메모를 더하면 그 이야기를 활용한다. 무가사에서도 전체 분위기와 여정의 흐름은 반영한다.

### 3.4 기록 기간과 앨범

**기록 묶음은 음악의 재료, 곡은 감상 결과, 앨범은 곡을 모은 소장 단위**다. 하루에 여러 번 운전하거나 중간에 쉬어도 하루·여행이라는 의미로 묶는 경험을 목표로 한다. 시동 종료 뒤 재개·여러 날 보관은 설계·검증 과제다.

| 이용 유형 | 경험 예시 |
| --- | --- |
| 하루의 곡 | 같은 날 여러 차례 이동한 실제 기록을 모아 그날의 곡 생성 |
| 월간 앨범 | 이미 만든 하루 곡들을 모아 ‘나의 8월’로 보관 |
| 여행의 곡 | 선택 여행 기간 전체를 한 곡으로 표현 |
| 여행 앨범 | 4박 5일 기록을 날짜별 곡으로 구성해 한 앨범으로 보관 |

여행 전체 한 곡과 날짜별 앨범은 선택 가능한 결과 형태다. 둘 다 자동 생성해 곡을 늘리는 기본 동작은 아니다. 여행 모드의 기본 추천 형태는 추후 결정한다. 기록 기준은 초기에 기억하고 결과 형태는 필요할 때만 바꾸게 한다.

월간·여행 앨범은 매번 전체 곡을 다시 만드는 기능이 아니다. 기존 곡을 묶고 순서·제목·커버를 다듬는다. 주행 없는 날을 채워 ‘매일의 기록’을 허위 완성하지 않는다.

### 3.5 차량과 폰의 역할

| 기능 | 차량 | 폰 |
| --- | --- | --- |
| SDK 기반 주행 기록 수집 | 제공 | 수집하지 않음 |
| 새 기록의 첫 곡 생성 시작 | 제공 | 제공하지 않음 |
| 기록 요약·곡·앨범 감상 | 제공 | 제공 |
| 기존 곡 재생성·가사 여부·장르 변경 | 정차 중 제공 | 제공 |
| 사진·메모 추가, 제목·커버 수정 | 정차 중 제공 | 제공 |
| 앨범 생성·곡 묶기·순서 변경 | 정차 중 제공 | 제공 |
| 설정 관리·보관·다운로드·공유·삭제 | 차량 환경에 맞춰 제공 | 제공 |

폰의 재생성은 이미 차량에서 곡을 만든 기록으로 새 버전을 요청하는 동작이다. 생성 처리의 실제 위치와 관계없이 적용하는 제품 정책이며, 폰의 기술적 불가능을 주장하는 것이 아니다. 폰에서 기존 곡이 없는 기록의 첫 생성을 실행하는 동작은 포함하지 않는다.

제목·커버·앨범 순서 정리는 곡을 다시 만들지 않고 수행한다. 가사·보컬 여부·장르를 바꿔 실제 음악을 변경할 때는 재생성이 필요하다. 버전 보존·교체와 동기화 충돌 처리는 설계에서 정한다.

### 3.6 대표 시나리오

**핵심 장면 — 함께 다녀온 주말 드라이브**

1. 운전자가 출발 전 기록을 시작한다. 추천 또는 지난 음악 설정을 그대로 사용한다.
2. 친구와 카페·전망대를 거쳐 돌아온다. 운전 중 기록을 위한 편집은 하지 않는다. 실제 방문으로 활용하는 장소는 지정·확인된 정보에 한한다.
3. 주차한 뒤 기록을 마친다. 기본 알림에서 한 번 눌러 음악을 만든다. 원하면 ‘처음 같이 본 바다’라는 메모나 사진을 보탠다.
4. 전체 기록에서 구성안을 만들고 AI가 곡을 생성한다. 출발의 도입, 중간 이동의 전개, 귀환의 마무리를 요청하고 실제 반영은 청취로 확인한다.
5. 함께 완성곡을 듣고 저장한다. 이후 폰에서 다시 듣고 제목을 다듬거나 같은 기록의 장르를 바꿔 재생성한다.

**지속 이용 장면 — 일상 기록**

하루 단위 이용자는 기록이 모인 날의 곡을 쌓고 월말에 기존 곡을 모아 월간 앨범을 만든다. 실제 습관이 되는지는 검증한다. 기본 생성은 한 번 누르기이며 자동 생성은 설정한 사람에게만 적용된다.

**확장 장면 — 4박 5일 여행**

여행 단위 이용자는 기간의 실제 기록을 묶고 여행 전체 한 곡 또는 날짜별 곡의 앨범으로 남긴다. 중간 주차·전원 종료·누락을 처리해야 하는 제품 요구이며 현재 실동작이 확인된 것은 아니다.

### 3.7 범위와 검증 순서

첫 가치 검증은 **실제 지원 차량 기록 → 주행 후 AI 곡 생성 → 저장·재감상**에 집중한다. 전체 제품 범위에는 기간 설정·선택 입력·앨범·폰 후속 이용을 포함한다. 아래 순서는 기능의 영구 제외나 임의의 출시 완료 기준을 뜻하지 않는다.

| 순서 | 확인할 것 | 다음 결정 |
| --- | --- | --- |
| 1 | 고정 기록 요약·구성안으로 실제 AI 생성곡 청취 | 감상 품질, 분위기·흐름 반영 가능성 |
| 2 | FusedLocation·Odometer의 실제 수신과 의미 | 사용할 데이터와 누락 처리 |
| 3 | 기록→구성안→생성→저장·감상의 연결 | 핵심 차량 경험 구현 가능성 |
| 4 | 기간 묶음·앨범·폰 편집·재생성·전달 | 여러 날 기록과 차량 밖 소장 경험 |

공모전의 첫 시연은 전체 여정 한 건과 실제 곡의 연결을 중심으로 한다. 월간 앨범이나 설정 화면만으로 핵심 가치를 대신하지 않는다. 제출용 7번은 비워둔다.

### 3.8 기대효과와 사업 가설

**가치:** 이동이 새로운 음악의 재료가 되는 창작 경험, 동행자와 다시 듣는 기억, 시간이 쌓일수록 늘어나는 개인 앨범.

**유입 가설:** 실제 샘플곡 체험 → 자기 드라이브 기록 → 첫 감상·저장 → 동행자 공유. 감상자 중 지원 차량 이용자가 새 기록을 만드는 전환은 따로 본다. 폰 감상자 모두를 차량 앱 설치 고객으로 세지 않는다.

**지속 이용 가설:** 여행 재감상, 다음 드라이브의 새 곡, 하루 곡의 월간 앨범과 여러 날 여행 앨범. 새 생성과 재감상을 나눠 평가한다.

**수익 가설:** 추가 재생성·스타일·내보내기 등의 유료 옵션을 검토하되 가격·무료 범위·재생성 한도는 미정이다. 임의의 결제 장벽을 확정하지 않는다. AI 호출·재시도·동기화·보관·전달 비용을 확인한다.

| 지표 | 측정 방향 |
| --- | --- |
| 첫 경험 완료 | 기록 시작→생성 성공→첫 감상·저장의 전환 |
| 개인화 가치 | 같은 스타일의 일반 곡과 여정 반영곡의 감상·소장 의향 비교 |
| 차량 정보 기여 | 위치만 쓴 경우와 차량 정보를 더한 경우의 구성안·음원 비교 |
| 재사용 | 새 주행곡 생성과 기존 곡·앨범 재감상 분리 |
| 앨범 가치 | 모음 구성 이후의 재감상·공유 |
| 운영 효율 | 생성 시간·실패·재시도·곡당 비용·폰 전달 성공 |

예상 MAU는 ‘실제 도달 가능한 지원 이용자 × 첫 경험 전환 × 해당 월 활동 비율’로 산정한다. 입력 자료가 없어 수치는 제시하지 않는다. D30 재방문은 첫 곡 생성 코호트의 후속 활동을 측정하되 다음 여행 기회·재감상을 함께 본다.

### 3.9 기획 수준의 기술 근거

- [FusedLocation 공식 문서](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/FusedLocation/intro): 위치 업데이트·영역 접근. 실제 수신·백그라운드 동작은 검증 전.
- [Vehicle 공식 문서](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/Vehicle/intro): Odometer·Wiper 등과 지원 확인. 개별 값·단위·차종은 검증 전.
- [구조화 AI 음악 생성 예시](https://elevenlabs.io/docs/eleven-api/guides/how-to/music/composition-plans): 구간별 스타일·길이·가사 지정. 서비스 선정·구성 준수·사용권·원가는 미정.
- [공식 심사 기준](https://appdevchallenge.auto-hmg.io/guide/judging-awards): 제출용은 차량특화성·창의성·기술 활용성·사업성을 각각 설명한다. 공개 배점은 없고 개발 자료는 선택 가산점이다.

## 4. NON-GOALS — 현재 중심 범위 밖

- 실시간 주행 음악의 구현을 필수로 만드는 것.
- 차량 제어·안전운전 점수·감정 진단·ADAS 카메라 풍경 인식.
- 전문 작곡 편집기·가수 목소리 모사·소셜 피드.
- 폰에서 독립적인 새 주행곡의 첫 생성.
- 모든 차종·완벽한 원곡 재현·초 단위 지도 동기화·매일 새 곡을 보장하는 약속.
- 기능 논의만으로 계정·폰 플랫폼·서버 방식을 확정하거나 구현을 시작하는 것.
