### 같은 실행 중 권한 갱신 — 사용자 취침 전

사용자 원문: “유료 음악 생성은 현재 충전해 둔 총 USD 5 이내에서 포괄 승인한다. 호출 횟수 제한은 없다. 실패·재시도 비용도 이 총액에 포함한다. 한도 안의 호출마다 다시 승인받지 않는다.”

- 이 갱신은 위의 추가 음악 승인 0/매회 별도 승인 조건을 대체한다. 기존 소진 원장을 초기화하지 않는다. 신규 음악 attempt마다 송신 전 USD 상한을 durable 예약하며 실패/접수 불명의 비용도 누적한다. 잔액 또는 승인 예산이 부족하면 음악 유료 송신만 닫는다. 음악 호출 횟수에 사용자 제한은 없고 총액이 상한이다.
- 추가 충전·자동결제·별도 유료 가사 API는 승인하지 않았다. 가사는 비과금 템플릿, 보호 저장된 기존 키를 재사용한다. 새 키 생성/직접 입력이 꼭 필요한 경우만 요청하며 키는 출력/채팅 요청하지 않는다.
- 환경/라이브러리/구현 방식/제출 대안은 근거를 남기고 자율 결정한다. 실제 백그라운드가 불가능하면 화면 유지형 제한 시연도 선택할 수 있다. 제품 백그라운드 요구는 후속에 보존하고 대역/미완료를 성공으로 표시하지 않는다.
- 사용자 약 5시간 부재를 전제로 응답 대기에 전체 작업을 멈추지 않는다. 비과금 구현/대역/저장·재생/영상/패키지 작업을 계속한다. inline·Guard 비사용·외부 게시/업로드·메일·배포 별도 승인·Windroid 중단은 유지한다.

이하 계획 수립 시점의 미착수/음악 승인 0 문구는 이력이며 현재 승인 범위를 취소하지 않는다. 실제 검증 결과/환경은 technical-validation.md에 누적한다.

### 제출 로컬 구현 선택과 근거

- 서버는 Kotlin/Ktor 유지. 이 PC에서 PostgreSQL 실행 파일이 없고 Docker daemon이 실행 중이지 않아, 제출용 단일 로컬 서버의 내구 작업 저장에 SQLite JDBC/WAL/FULL transaction을 선택했다. 실제 DB로 중복·예산·재시작을 검사하며 메모리 대역으로 DB 검증을 대신하지 않는다. 운영/다중 worker PostgreSQL 확장은 후속 P3/P8에 보존하며 설계 원문을 고치지 않는다. 현재 사용자 지시의 라이브러리/제출 대안 자율 판단 범위다.
- 로컬 TLS 자체 서명 공개 인증서를 APK에 포함하고 서버 private key/password는 .local 보호 저장/DPAPI에 둔다. Android Keystore 기기 키의 공개키를 관리자가 명시 등록하며 `kind=CAR` API 자가 선언 경로를 제공하지 않는다. 서비스 수준 로그인/차량 증명 완료를 주장하지 않는다.
- 음악 후보는 기존 검증된 Lyria3.5. 2026-11-12 [공식 가격](https://ai.google.dev/gemini-api/docs/pricing) 재확인: 기본 곡당 USD0.08. 원장은 기존 3곡에 보수적 USD0.30을 포함하고, 신규 시도마다 USD0.10 예약을 유지한다. 실패·접수 불명도 반환하지 않는다. 승인 총액 USD5를 넘지 않으며 실제 청구 확인과 예약 추정은 구분한다. 필요한 새 곡만 생성하고 예산 소진을 목적으로 호출하지 않는다.
- S2 및 S3 최초 저장/재감상은 기존 MP3를 FIXTURE/새 생성 아님으로 표시한다. 이 경로 확인 전 live dispatch는 기본 꺼짐을 유지한다. 기존 음악 probe의 소진 원장은 수정하지 않는다.

> **후속 실행자:** 별도 착수 지시 뒤 활성 Superpowers executing-plans로 한 명이 승인 범위를 이어서 수행한다. 기본은 inline 실행과 묶음 단위 자체 검토다. Workflow Guard는 기본 사용하지 않는다. 계획과 설정은 실행 승인이 아니며 미승인 묶음·선행 작업·후속 기능을 자동 실행하지 않는다.

**목표:** 11월 15일 제출 전에 실제 차량 SDK 기록→여정 요약→차량에서 시작한 실제 AI 곡→저장·재감상과 영상을 확보한다. 실행 계획은 S1 수집, S2 생성 연결, S3 저장·재생, S4 영상·제출 준비의 네 묶음이다. 제출 범위를 완료해도 전체 제품·이전 P0~P6 전체 검증 완료를 뜻하지 않는다.

## 7. 실행 방식과 후속 인계

마감 전 기본은 **inline + 묶음 단위 자체 검토**, Guard 기본 비활성이다. Guard의 새 실행/환경 의존을 제출 선행 조건으로 만들지 않는다. 이미 승인된 작업을 격리/독립 리뷰할 분명한 이점이 있을 때만 선택적으로 사용하며, 준비 명령도 명시적 opt-in을 요구한다. 한 구현 lane·승인 범위·별도 유료 승인 규칙은 실행 방식과 관계없이 유지한다. Guard/설정 검사는 SDK/제품 증거가 아니다.

각 묶음은 핵심 로직/DB/API의 위험 사례와 실제 SDK/미디어/복구 관측으로 검증한다. 없는 테스트를 통과했다고 쓰거나 전체 suite·임의 coverage/SLA·모든 예외를 새 제출 장벽으로 추가하지 않는다. 제품 검사는 지금 실행하지 않는다.

실행 뒤에만 technical-validation.md에 묶음별 코드/환경/명령·run 위치·입력/음원 해시·결과·한계를 추가한다. 후속 P 체크리스트는 실제 충족한 세부 항목만 연결하며 S 완료를 P 전체 완료로 승격하지 않는다. 승인 범위가 끝나면 종료하고 미승인 묶음/후속으로 자동 진행하지 않는다.
